# Interview Scheduler

A small web app where an interviewer publishes available interview slots and candidates book one with their name and email. A booked slot disappears from the list immediately, and double bookings are impossible.

- **Live app:** https://scheduler-one-lac.vercel.app
- **API (Swagger UI):** https://scheduler-yeuo.onrender.com/swagger-ui.html
> The backend runs on a free Render instance that sleeps when idle. The first request can take up to a minute; please retry once.

## What I built

**Candidate view (`/`)**
- Browse available slots grouped by day
- Book a slot with name, email and optional notes
- A short, friendly confirmation message **generated by Gemini** (my AI extra)

**Host view (`/host`)**
- Create slots (date, start time, duration, optional position)
- See all slots with their status, and delete unbooked ones
- See every booking with the candidate's details

**Rules enforced by the backend**
- Slots must start in the future and cannot overlap each other
- A slot can be booked only once; the loser of a race gets a clear `409 Conflict`
- Booked slots cannot be deleted
- Validation errors come back as `400` with per-field messages

No login, a single host and a single time zone (Europe/Skopje), as allowed by the brief.

## Run it locally

**Prerequisites:** JDK 21, Node 20+, Docker.

**1. Database**
```bash
docker compose up -d
```
Postgres is exposed on `localhost:5434` (user, password and database are all `scheduler`).

**2. Backend**
```bash
cd backend
./mvnw spring-boot:run        # Windows: .\mvnw.cmd spring-boot:run
```
Runs on http://localhost:8080. Flyway creates the tables on startup. Swagger UI: http://localhost:8080/swagger-ui.html

**3. Frontend**
```bash
cd frontend
npm install
npm run dev
```
Runs on http://localhost:5173. By default it calls `http://localhost:8080`.


### Configuration

All values have local defaults. Override them with environment variables:

| Variable | Used by | Purpose |
|---|---|---|
| `DB_URL`, `DB_USER`, `DB_PASSWORD` | backend | Database connection (JDBC URL) |
| `APP_CORS_ALLOWED_ORIGINS` | backend | Comma-separated allowed frontend origins |
| `GEMINI_API_KEY` | backend | Enables AI messages; without it a template message is used |
| `GEMINI_MODEL` | backend | Gemini model name (default set in `application.yml`) |
| `TZ` | backend | Server time zone (`Europe/Skopje` in production) |
| `VITE_API_URL` | frontend | Base URL of the backend |

## API

| Method | Endpoint | Description |
|---|---|---|
| `POST` | `/api/slots` | Create a slot |
| `GET` | `/api/slots?status=AVAILABLE` | List slots (optionally filtered) |
| `DELETE` | `/api/slots/{id}` | Delete an unbooked slot |
| `POST` | `/api/slots/{id}/bookings` | Book a slot (`409` if already taken) |
| `GET` | `/api/bookings` | List all bookings (host) |
| `POST` | `/api/bookings/{id}/confirmation` | AI-generated confirmation message |

## Key decisions

- **Monolith with feature packages.** One deployable, easy to run and reason about. Services are split into an interface and an implementation, and controllers depend on the interface.
- **DTOs as Java records.** Entities are never exposed through the API. I wrote the matching TypeScript types by hand because the API is small; generating them from OpenAPI would be the next step.
- **No double bookings, two layers of protection.** An optimistic lock (`@Version`) on the slot catches concurrent bookings in the application, and a `UNIQUE` constraint on `booking.slot_id` is the final guarantee in the database. Both map to a `409` response.
- **Flyway owns the schema.** Hibernate only validates it (`ddl-auto: validate`).
- **AI is isolated from the booking flow.** The confirmation message is a separate endpoint called after the booking succeeds. If Gemini is slow, rate-limited or the key is missing, the user gets a template message instead, so booking never depends on the LLM. Only the candidate's first name and slot details are sent to the model, never their email.
- **Secrets stay in environment variables.** Nothing sensitive is committed.
